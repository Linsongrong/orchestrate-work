# Routing Policy

This is the sole authority for assurance, minimum-sufficient work, route selection, ownership, evidence, side effects, recovery, and phase transition. The controller records the applicable decisions in the unified dispatch record in [task-contract.md](task-contract.md).

## Assurance And Minimum Work

Set one profile before substantive orchestration work, including primary-owned execution. An explicit user selection wins. Otherwise use `prototype` only for an explicitly exploratory feasibility decision, proof of concept, spike, or disposable minimum experiment; use `formal` for durable, mergeable, complete, production-use, or ambiguous nontrivial work; use `release` only when release or readiness is explicit. "Quick", "MVP", and "try" alone do not lower durable implementation. A phase may be raised; lowering requires explicit user authorization and applies only to unstarted work.

| Profile | Required assurance | Avoid by default |
| --- | --- | --- |
| `prototype` | One focused independent decision Gate per hypothesis experiment, after executor author checks | Separate Gates for subchanges, broad regression, full-history validation, or low-value sidecars |
| `formal` | Prototype risk floor, proportional independent verification of important artifacts, and final integrated verification | Reducing concrete safety, authority, or external-effect checks for speed |
| `release` | Formal assurance plus reproducible environment evidence, external-dependency review, and readiness checks | Calling an unverified environment or dependency release-ready |

For a prototype, the risk floor is only checks preventing a wrong experiment conclusion, authority/side-effect violation, irreversible harm, unreviewable result, or responsibility-boundary failure. Record hypothesis, minimum experiment, decision threshold, nonblocking backlog, and Gate/repair budget. Keep tightly coupled design, adapters, mocks, implementation, and author checks in one candidate with one owner, primary or delegated. Add work, an agent, integration, or a check only when it changes an acceptance decision, protects a trust boundary or side effect, enables valid evidence reuse, or resolves cross-owner coordination. Each retained check needs a concrete, unique failure mode. Backlog speculative completeness; uncertainty is not a present requirement.

## Routes, Reuse, And Capacity

Route a complete **work segment**, not each command: one coupled objective with an explicit completion boundary, including its ordinary diagnosis, implementation, author checks, and narrow repairs. Choose model and reasoning effort together under the user's quality, budget, and time constraints. Compare expected execution, context transfer, coordination, repair, and verification costs; a cheaper token rate or lower high-tier share alone does not prove a cheaper completed task.

Use these starting recommendations only when available and not overridden by the user:

| Work segment | Starting route |
| --- | --- |
| Uncertain, tightly coupled investigation and implementation where repeated decisions depend on retained context | Astra/medium; prefer an already-selected Astra primary owning the main line |
| Substantial bounded routine implementation, diagnosis, or integration | Terra/medium |
| Batched deterministic lookup, extraction, or checks that justify an agent | Luna/low or medium; use direct tools for tiny checks |
| Demanding bounded judgment, or a suitable alternative when Astra is unavailable | Sol/medium, with a concrete capability reason |

These are provisional workload defaults, not a global Astra requirement or proof of savings. Preserve an explicitly selected model/effort within the scope of that choice; a skill cannot switch the running primary model. Above a cheaper plausible route, record the specific capability or continuity gap and segment boundary, not just "complex", "important", or "high risk". Higher effort needs a concrete reasoning gap; above `high`, require new evidence of lower-effort insufficiency, without a mandatory failed trial at every level. For an existing Astra conversation, preserve its effective effort initially and reassess at a segment boundary rather than blindly resetting to medium. Do not assume Astra can be explicitly selected as a child unless the current tool exposes it.

At each followup confirm the same segment, ownership, authority, budget, and recommended route still apply. Recompute model and effort at completion or a substantial change of work, material assumptions, rejection, nonconvergence, or recovery. Adjacent mechanical steps and ordinary author debugging stay with the owner. A substantial separable routine batch starts a new segment: prefer a sufficient cheaper route, and do not extend high-tier ownership merely for convenience. Before any Astra/Sol segment, including primary-owned work, record a bounded work budget; renewal requires a fresh concrete capability or continuity reason. Without usage telemetry, use a completion boundary or experiment/repair allowance rather than inventing a token cap. Internal reassessment does not require user approval unless scope or actual authority/budget changes. Audit measured usage when available and label unmeasured savings as estimates. Internal compute and worker-initiated external paid API calls remain separate budgets.

Every dispatch explicitly contracts model and effort, including intentional inheritance. Use `<role>_<work>_<model>_<effort>` as an observability hint and record requested/actual route. For fresh workers, use `fork_turns="none"` and compact task-local context where supported. Reuse only for matching role, lineage, scope, authority, budget, and recommended model/effort. If rerouting is required and the tool cannot change the route, create a suitable fresh worker with an explicit handoff. `followup_task` does not itself expose a route change; do not infer one from API features. Cache can favor continuity but never assumes cross-agent/model hits or replaces a distinct verifier. Record an unavailable-route fallback and its confidence effect; do not silently claim the requested model ran.

Dispatch ready, disjoint work in a wave within capacity; preserve serial dependencies and reserve verification capacity where useful. One direct child layer only: no nested orchestration. Use direct child agents by default; suggest a user-owned task only for long-lived independently steerable work or strong worktree isolation, and only with explicit user authorization.

## Ownership, Evidence, And Side Effects

Give every author exclusive ownership, including a primary acting as executor or integrator. Record its objective/scope, route and cost reason, completion/evidence requirements, and authority/budget without a self-dispatch contract. All authors follow the minimum-implementation and targeted-check rules in [task-contract.md](task-contract.md). A delegated worker's no-delegation preamble does not turn the primary author into a worker. Retain a non-executing controller where concurrent oversight or consequential conflict needs an uninvolved decision owner. Transfer ownership explicitly before another agent repairs or integrates; freeze candidate paths during independent verification.

The verifier is read-only, did not implement the candidate, and receives authoritative criteria, candidate identity, and raw evidence in fresh task-local context, without the author's private reasoning or desired verdict. Choose sufficient verifier capability for the conclusion, not automatically a cheaper model than the author. Authors cannot issue their own independent verdict. A primary author may record acceptance only from a matching immutable independent accept verdict; it cannot override rejection, alter the verdict, or relax criteria to approve its work. Resolve contested evidence or proposed acceptance changes independently before accepting. Integration changes need independent verification of the resulting candidate.

Assign check ownership before dispatch. Before evidence reuse, cross-owner/concurrent/mutable-state handoff, or independent verification, confirm the stable candidate identity or digest and required receipt. Reuse evidence only when identity, command, environment, result, and owner still match. Never transfer evidence from a superseded identity. Ordinary local low-risk work may use declared artifacts and targeted author evidence without a digest. A verifier starts only on a complete candidate, applicable verified handoff/identity, current author evidence, and no unresolved ordinary author-debugging issue; partial is never Gate-ready. A handoff mismatch is incomplete, not a quality Gate.

Authorize and account for costly, mutable, irreversible, sensitive, or external side effects before execution or dispatch, including primary-owned work. State the actual authority and a named budget; `none` means none is allowed or needed. Keep secrets only in approved ephemeral channels unless the user authorizes persistence. Before consuming a budget, confirm remaining allowance. A pre-action validation failure consumes none; an attempted action with unknown outcome consumes one until reconciled. Every retry consumes the named budget; never retry silently. Stop retries on budget exhaustion, no new evidence, or nonconvergence, without a universal numeric retry limit. Exhaustion blocks only that side effect and retries, not otherwise-ready zero-consumption work. Mutable remote state needs an observed-state receipt, freshness bound, and reread trigger when it can change before dependent mutation or acceptance.

## Monitor, Recover, And Advance

Use completion gates and soft timeouts proportional to expected work and tool latency, never a universal minute limit. At timeout request one compact progress report; continue healthy, in-scope work producing new evidence. Interrupt or reroute only for stall, repeated failure, scope drift, noncritical hardening consuming the main line, or critical-path block without useful progress. Use adaptive time or decision heartbeats for long-running phases; synthesize objective, decision evidence, convergence/budget, next decision, and needed user action rather than forwarding raw worker progress.

First verifier failure returns to the original author, primary or delegated, when its route and segment budget remain justified; otherwise transfer repair ownership and functional base to a suitable executor. In prototype, permit one narrow repair and re-Gate for the same hypothesis; another rejection requires reassessment and proceeds only with new evidence, acceptance criticality, and credible convergence. In formal/release, continue acceptance-critical repair while iterations produce new evidence and converge. Repeated failure, no new evidence, noncritical hardening, or two nonconverging rounds requires reassessing contract, assumptions, and approach before any model/effort escalation. Then backlog, redesign, reroute, or request authority as appropriate.

Preserve accepted artifacts and recover ordinary command, tool-path, JSON/reference, transient restart/socket/readiness, and healthy-observation-timeout faults within side-effect, retry, and convergence limits. Those faults do not justify partial. Stop a route after reassessment if it still fails; use another in-scope route or report a concrete blocker/request user decision. Admit discovered work only when acceptance-critical, blocking, or assumption-disproving; otherwise backlog and ask before material scope change. An emergency takeover of delegated work requires the previous writer to settle, recorded ownership/authority transfer, and independent verification.

After acceptance, record completed deliverables, non-goals, latest verdict, next objective, profile, and remaining/new authority. Keep a compact final route audit per work segment: owner, requested/actual model and effort, continuity or handoff reason, budget, and measured usage when available. Include primary-owned segments and flag unjustified high-tier routine batches, unnecessary handoffs, or unsupported savings claims. Start the next phase only when already authorized; otherwise ask the user. A required Gate not yet recorded is pending verification, not completion. On user-direction change, assess impact, stop only affected branches, revise records, and reject stale results.

## Model Guidance Basis

The workload defaults draw on [Building agents](https://developers.openai.com/tracks/building-agents), [Astra guidance](https://developers.openai.com/api/docs/guides/latest-model), and [Multi-agent](https://developers.openai.com/api/docs/guides/responses-multi-agent), reviewed 2026-09-05. Refresh official guidance when maintaining these defaults; ordinary dispatch uses exposed runtime capabilities and needs no repeated documentation search. API features do not establish what this Codex runtime exposes.
